# 07 — Context delivery

[Русский](ru/07-доставка-в-контекст.md) · **English**

So an agent remembers that memory exists and knows how to use it, iapeer-memory delivers a few things straight into the system prompt — as a fragment layer (iapeer's layer 5):

- **the guide** — how to write into memory: which typed folder to write to, how to use search, the status scales, the formatting rules;
- **the tag dictionary** — which tags already exist and where each one's boundary is, so the author can choose a tag before the first search;
- **the author's note index** — a map of what this agent already has in memory, by topic.

The guide is shared across the team (`~/.iapeer/fragments/iapeer-memory.md`); the tag dictionary and the index live in the peer's personal fragment (`<peer-folder>/.iapeer/fragments/iapeer-memory.md`), together with a store-paths block. iapeer stitches all of it into the system prompt: the shared guide first, then the personal layers.

## The author's note index

The index is a slice of the agent's memory: a list of its notes, grouped by section. Selection depends on the zone: operative memory is keyed by the PHYSICAL folder (everything under `06_…/<agent name>/`, whoever wrote the note — the folder owner, a DreamWeaver consolidation, or a colleague's signed feedback), canon by authorship (`author` or `coauthors`). Operative memory comes first (it's consulted most often), then knowledge, decisions, projects, ideas, lists:

```text
## Operative memory
- [[Title]] · pitfall · current · "description" · 3 links · 2026-06-13
…
## Knowledge
- [[Title]] · current · Security, LLM · 5 links · 2026-06-13
…
```

The line depends on the zone. **Operative memory**: `[[title]] · subtype · status · "description" · link count · date` — it carries the subtype (pitfall, reference…) and a description. **Canon**: `[[title]] · status · tag(s) · link count · date` — tags take the place of the subtype and description: a canon note is classified by its tag, not a personal description. In both, the link count and date come last.

To keep the index from sprawling, each section has quotas, and stale notes don't enter the index — search still finds them. The index is a "what do I have" signpost; for the current content the agent goes to `memory_search`, which sees the entire team store, not just the author's notes.

## Freshness

The index is generated by `memoryd` and rewritten on vault changes. The key property: the system-prompt layer is rebuilt on every session start (for Claude and Codex, a session start means a new process with a freshly assembled prompt). So a fresh start always carries a current map.

The index can go stale only inside a continuously running session — while the process lives its system prompt doesn't change, and the vault may have moved on. That's not a problem: the index is deliberately secondary, the truth about content is in `memory_search`, which reads the index in real time. A restart, or sleep followed by wake, pulls in a fresh index.

Fragments are written atomically — the index is rewritten often and may coincide with a session start, so the replacement is whole-file, with no risk of reading half a file.
